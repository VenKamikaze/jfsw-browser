## 2. The shape of the program

- `main` (`jfbuild/src/sdlayer2.c:254`) -> `app_main` (`src/game.c:3372`): arguments, `preinitengine()`, `CONFIG_ReadSetup()`, `ScanGroups()`, `-net`, optional startup window, `initgroupfile(grp)`, the rest of the arguments (`game.c:3672-4078`), then `Control()` (`:4080`).
- `Control` -> `InitGame` -> `GameIntro` (logo, intro movie `playanm(0)`, `MenuLevel`) -> `NewLevel` loop. Each `NewLevel` is `InitLevel` + `RunLevel` + `StatScreen` + `TerminateLevel` (`game.c:1566-1625`). In demo mode `NewLevel` calls `DemoPlayBack` instead of `RunLevel`.
- Exits: `QuitFlag` leaves the `Control` loop and calls `TerminateGame`. Many error paths and `swexit` call `exit()` directly from the middle of loops (`net.c:588`, `demo.c:234,572`, `sync.c:525`, `MultiSharewareCheck`). Under Emscripten each of them is a termination of the program.
- A SIGTERM (or any `SDL_QUIT`) sets `quitevent` in `handleevents()`; the level loops turn it into `QuitFlag`, and the game exits with status 0 (run). `scripts/run-headless.sh` uses this to stop a run.

| `int getpacket(int *other, unsigned char *buf)` | yes (`net.c`) | Reads the socket, handles acks, retransmits, the `0xaa`/`0xab` start-up protocol; returns the length of the next packet from any player, or 0. With `buf == NULL` it only processes (used by `flushpackets` and the start-up cycle). |
| `void flushpackets(void)` | yes (`game.c`, 5 sites) | `getpacket(&i, 0)`: acks and resends only. |

Start-up protocol (master/slave): a slave sends the master `0xaa` pings every 250 ms (`initmultiplayerscycle`, `mmulti.c:815-835`). The master answers each new address with `0xab {slot, numplayers, netready}` (`getpacket`, `:1066-1085`) and records its address (`savesnatchhost`). The master sets `netready` when every slot has an address, has been heard from, and has not timed out (`PRESENCETIMEOUT 2000` ms). The slave takes its slot from the reply (`myconnectindex = pakbuf[k+1]`, `numplayers = pakbuf[k+2]`, `:1130-1145`) and is ready when the master says so. Pings are answered during the game too, with the same slot, so a restarted client gets its slot back; a stranger arriving when all slots have addresses gets no reply.

Other points for brief 01:

- Every packet starts with `crc16ofs` (2 bytes) and ends with the CRC16. A regular packet carries `icnt0` (4 bytes) + 32 bytes of ack bits + the packets. Start-up packets use `icnt0 == -1`.
- Slaves in master/slave mode only talk to the master (`getpacket`, `:1020`, `:1222`). The game itself relays between slaves (`PACKET_TYPE_PROXY`, `net.h:34`, `NetBroadcastMode`).
- `netinit` (`:130`), `netsend` (`:267`) and `netread` (`:400`) are the only socket users: that is where a vnet backend goes. `netuninit` is non-static (`:114`).
- Timing in mmulti uses its own static `GetTickCount()` (a `gettimeofday` wrapper, `mmulti.c:53`), not `totalclock`.
- `jfbuild/src/mmulti_null.c` is an unused stub of the same API (single player only). The `Makefile` builds `mmulti.c` (`jfbuild/Makefile:82`); `mmulti_null.c` is only mentioned in `Makefile.deps:20`. It is a single-player stub (`initmultiplayersparms` returns 0, no packets), so it is no use for netplay, and it defines an extra `isvalidipaddress` that is not in the header.
- Packet type bytes the game puts in the first byte of its payloads: `net.h:27-47` (`PACKET_TYPE_MASTER_TO_SLAVE 0`, `SLAVE_TO_MASTER 1`, `MESSAGE 4`, `BROADCAST 17`, `PROXY 19`, `NEW_GAME 30`, `PLAYER_OPTIONS 32`, `RTS 33`, `MENU_LEVEL_QUIT 35`, `VERSION 38`, `NULL_PACKET 127`, `PLAYER_READY 250`).

## 4. Startup order and the command line (briefs 03, 05)

`app_main` argument handling happens twice: a first scan for `-setup`, `-nosetup`, `-net` and `-?` (`game.c:3467-3510`), and a second, full scan after the GRP is chosen (`:3672-4078`). Arguments seen here, all with a leading `-`:

- `-nosetup`, `-setup`: startup window control (`game.c:3477-3485`).
- `-net <args…> [--]`: passed to mmulti (§3).
- `-level<N>`: start level N (1-based index into `LevelInfo`) at once, skipping the intro and menus (`game.c:3799`); `GameIntro` returns early when `UserMapName` is set (`:2852`). `-s<N>` skill 1 to 4 (`:3807`).
- `-dr<name>`, `-dp<name>`: demo record and play (§7). `-nodemo`: no attract-mode demos (`NoDemoStartup`, `:3741`).
- `-name <player>`, `-g<file>`, `-h<def>`, `-turnscale`, `-movescale`, `-short`, `-nometers`, `-cheat`, `-autonet <rules…>`.
- `DEBUG` is `0` (`game.h:32`), so the `#if DEBUG` options (`-allsync` at `game.c:3745-3751`, `-commbat`, `-coop`, `-bots`, `-ddr`, `-cam`, `-debugsecret`, …) do not exist in this build. `-f2`/`-f4`/`-f8` (`MovesPerPacket`, `game.c:3762-3775`) and `-nopredict` (`PredictionOn`, `:3782-3786`) are **not** inside `#if DEBUG` and do work.

Files and directories, in order of use:

1. `CONFIG_ReadSetup()` (`game.c:3516`) reads `sw.cfg` (`SETUPFILENAME`, `src/common.h:67`, `config.c:581`), relative to the current directory. At that point the current directory is: the directory the game was started in, or `~/.jfsw` (see §6) once `chdir(dirpath)` has run (`game.c:3446`).
2. `ScanGroups()`, `IdentifyGroup()`, then `initgroupfile(grpfile)` (`game.c:3617`, "GRP file: …"), `DetectShareware()` if no recognised GRP.
3. `InitGame`: palette, `LoadDemoRun()` reads `demos.run` and `demotxt.run` with plain `fopen` (`game.c:763-790`), i.e. **from the current directory, not from the GRP**; the shareware GRP has no such files, so no attract-mode demos (run).

## 5. Where the game blocks (brief 02, ASYNCIFY)

The event pump is `handleevents()` (`jfbuild/src/sdlayer2.c:1259`; `SDL_PollEvent` loop; sets `quitevent`, updates keyboard/mouse state and the OSD). The frame flip is `nextpage()` (`jfbuild/src/engine.c:7968`) -> `showframe()` (`sdlayer2.c:1064`) for 8-bit modes. The clock is `totalclock`, advanced by `sampletimer()` (`sdlayer2.c:635`, from `SDL_GetPerformanceCounter`; there is **no timer thread or interrupt**: it is polled: `handleevents()` itself calls `sampletimer()` (`sdlayer2.c:1431`), so every event-pumping loop advances `totalclock`; `faketimerhandler` (starts `net.c:812`, call at `:829`) and `getpackets()` (starts `net.c:1136`, call at `:1143`) call it too; and `inittimer(120, NULL)` registers no callback). Nothing in the game sleeps: every wait is a busy loop on `totalclock`, `handleevents()` and `getpackets()`.

## 6. File paths and the search path (brief 03)

The "search path" is a stack in `jfbuild/src/cache1d.c:253-264`: `addsearchpath(dir)` (`:264`) pushes a directory, which must exist. Lookup is `findfrompath` (`:298`): first `./<name>` (the **current directory**), then each search-path directory from the most recently added to the first. Leading `/` are stripped from the name and `..` is collapsed, so an absolute path cannot be opened this way.

`app_main` adds, in this order (`game.c:3388-3445`): `DATADIR` (`/usr/local/share/games/jfsw` by default, from the `Makefile`), the directory of the executable (`Bgetappdir`, `jfbuild/src/compat.c:118`; on Linux from `/proc/<pid>/exe`, `:139`), the global support dir (`Bgetsupportdir(TRUE)`, NULL on Linux), and then either:

- the current directory, if a file named `user_profiles_disabled` exists in it ("portable" mode; no `chdir`), or
- `$HOME/.jfsw` (created if missing), followed by `chdir($HOME/.jfsw)`.

Lookup order (`findfrompath`) is therefore: current directory, then (portable) the same directory again or (default) `~/.jfsw`, then the executable's directory, then `DATADIR`. The GRP scan (`klistpath`) walks the same places: the current directory first, then the stack. In the default mode the current directory at scan time is `~/.jfsw` (the `chdir` comes first), not where the game was started.

What goes where:

| File | Written/read | Relative to |
|---|---|---|
| `sw.cfg` | read at start (`CONFIG_ReadSetup`), written by `CONFIG_WriteSetup` (`config.c:762`) on exit and when settings change | current directory (`~/.jfsw`, or the portable cwd) |
| `sw.log` | `buildsetlogfile("sw.log")` (`game.c:3452`) | same |
| `grpfiles.cache` | `grpscan.c:223` | same |
| `*.dmo`, `*.dms` | demo record (`fopen`) and sync files | same; demo *reading* uses `kopen4load` (§7) |
| save games | `src/save.c` | same |
| the GRP(s) | scanned by CRC32 in the current directory and the search-path directories | cwd at scan time (`~/.jfsw` in default mode) + search path |
| `sw.def`, `swvoxfil.txt`, `swplock.txt`, `swcustom.txt` | `kopen4load`: loose files first (cwd, search path), then the GRP | |

`kopen4load(name, 0)` (`cache1d.c:577`) tries a loose file first via `openfrompath`, then ZIPs added with `-g` (kplib), then the group files from the last added to the first. So a loose file in the search path overrides the same name inside the GRP. `initgroupfile` (`:433`) accepts a ZIP (checked by magic number) as well as a GRP.

Things to know for the browser: there is no `HOME`, `/proc` or `DATADIR` there. In Emscripten's virtual filesystem, put the GRP in the current directory at scan time or in a directory that `addsearchpath` is given. The portable mode (`user_profiles_disabled` in the cwd) already does that and keeps the config in the cwd, so a data folder written by the page needs no engine change. Detection reads the whole GRP once for its CRC32 (26 MB, about 0.1 s natively), then caches the result in `grpfiles.cache`.

## 7. Demos and bounded runs (briefs 01, 02, 04)

There is no "run N frames then quit" option (checked: no such argument in `app_main`). What exists:

- **`-dp<name>` plays back `<name>.dmo` and then exits by itself with status 0**: at the end of `DemoPlayBack`, `if (DemoDone && !DemoMode && !NewGame) { TerminateLevel(); TerminateGame(); exit(0); }` (`src/demo.c:568-573`). It needs the level too: `-level1 -dpname`. Without `-level#` the playback tries `title.map` and ends with "Level not found: title.map" (run). The `.dmo` is read with `kopen4load` (`demo.h:54-58`, `DEMO_FILE_GROUP`): current directory, search path, then the GRP. It runs flat out (no frame limit): a 6-second demo plays in about 6 CPU-seconds natively because it renders every frame (run).
- **`-dr<name>` records `<name>.dmo`** from the start of the level until the game is stopped (no end). It records one player only (`DemoRecCnt`, `demo.h`). Stop it with SIGTERM: the game exits cleanly with 0. The demo is written in 2048-packet buffers (`DEMO_BUFFER_MAX`), so a short recording has data up to the last full buffer. A demo header holds the map name, song, level, the players' start positions, `Skill` and the `gNet` struct (`DemoWriteHeader`, `demo.c:169`); with `fwrite` of C structs, so whether a demo recorded on 64-bit x86 plays back on 32-bit wasm is **unverified** (brief 02 must check).
- **`-demosyncrecord` and `-demosynctest`** (with `-dp`): while a demo plays, `demosync_record()` (`sync.c:498`) writes nine bytes per tic (one per sync function, §8) to `<name>.dms`; `demosync_test()` (`sync.c:511`) reads them back and compares. On a mismatch it prints `Demo out of sync - Sync Byte Number %d - Iteration %d.` to **stdout** and `exit(0)`: **the exit status is 0 on failure**, so a test must grep for that text (run: recorded and re-tested a demo with no mismatch; with an empty `.dms` it reports "Sync Byte Number 0 - Iteration 1"). The `.dms` must be recorded during a *playback* (`-dp -demosyncrecord`), not during `-dr`: `demosync_record` is only called from `DemoPlayBack` (`demo.c:504`). Both flags set `NumSyncBytes = 8` (`game.c:3920, 3927`).
- Demo time is `totalclock`-independent: playback consumes one recorded input packet per `synctics`, so the result depends on game logic only (and on `randomseed`). This is what the determinism checks between native and wasm rely on.
- Shareware has no attract-mode demos: `demos.run` is a loose file (`game.c:763`) and the GRP has no `.dmo` (run: none listed).

Recipe (all with `scripts/run-headless.sh`, same `--workdir`):

```sh
scripts/run-headless.sh --timeout 6 --workdir /tmp/w -level1 -drdemo1     # exits 124 (stopped), writes /tmp/w/demo1.dmo
scripts/run-headless.sh --workdir /tmp/w -level1 -dpdemo1                 # exits 0 by itself
scripts/run-headless.sh --workdir /tmp/w -level1 -dpdemo1 -demosyncrecord # writes demo1.dms
scripts/run-headless.sh --workdir /tmp/w -level1 -dpdemo1 -demosynctest | grep -c "out of sync"   # expect 0
```

## 8. Sync data (briefs 01, 02, 04)

- **What is hashed.** `src/sync.c` has nine functions, each returning one byte (a CRC16 folded to 8 bits, `updatecrc`, table from `initsynccrc`, `sync.c:43-60`): `RandomSync` (the low 16 bits of `randomseed`, and when `NumSyncBytes == 1` also `PlayerSync`, `PlayerSync2`, `MissileSync` folded in), `PlayerSync` (x, y, z, angle of each connected player), `PlayerSync2` (horizon, health, `bcnt`), `SOSync` (sector objects), `EnemySync`, `MissileSync`, `ShrapSync`, `MiscSync`, `MissileSkip4Sync` (positions and angles of the sprites in those status lists). Only the low byte of each coordinate goes in (`& 255`). Names in `SyncNames[]` (`sync.c:280`). `MAXSYNCBYTES` is 16 (`net.h:51`).
- **How many.** `NumSyncBytes` defaults to 1 (`sync.c:36`), so in a network game only the `RandomSync` byte is exchanged; `-demosync*` set 8; `-allsync` (16) is `DEBUG`-only and so absent.
- **When, and what is sent.** `getsyncstat()` (`sync.c:309`) fills the player's `syncval` FIFO from `domovethings` (`player.c:7860`), only if `CommEnabled && CommPlayers >= 2`. `SYNC_TEST` is `TRUE` (`net.h:50`), so the branch at `player.c:7896-7900` is compiled in: it runs `getsyncstat()` when `!(movefifoplc & 0x3f)` (every 64th move) **and, through the `#ifdef DEBUG` `else` (taken, since `DEBUG` is defined as `0`), on every other move too**. So in practice it runs on every move: **one sync check per game tic, not one per 64** (measured in brief 01: 596 checks in 600 tics). **Only the master compares.** A slave stores the master's bytes (`PACKET_TYPE_MASTER_TO_SLAVE`, `net.c:~1245-1262`; the call to `GetSyncInfoFromPacket` there is commented out with "This doesn't work right in this case") but never sets `syncstat`, so on a slave "GAME OUT OF SYNC" is never drawn and nothing is logged; the master compares each slave's bytes (arriving in `PACKET_TYPE_SLAVE_TO_MASTER` packets) with its own. A network test must therefore look at the master. The master's own copy of a slave's bytes is checked against the master's, so a desync of any player, the master included, shows on the master. Each call stores `NumSyncBytes` bytes (1 by default; 9 are computed per call, `SyncFunc[]`). What goes on the wire: `AddSyncInfoToPacket` (`net.c:796`) appends up to 4 pending entries of `NumSyncBytes` bytes each to a movement packet; `GetSyncInfoFromPacket` (`sync.c:416`) compares each other player's value with the master's (`connecthead`) and sets `syncstat[sb] = 1` on a difference.
- **How a desync is reported.** `SyncStatMessage` (`sync.c:336`, called from the draw code): with `NumSyncBytes == 1` it draws "GAME OUT OF SYNC!" and "Restart the game." over the menu font (no console output, no exit); with more it prints "GAME OUT OF SYNC - <name>" and the first failure. Brief 01 added the log line: `GetSyncInfoFromPacket` now prints `GAME OUT OF SYNC: tic <sync check index>, sync byte <n> (<name>), player <p> differs from the master` once per sync byte, counts every comparison in `SyncChecks` and every mismatch in `SyncMismatches` (`sync.c`; master only, see above). The tests grep `OUT OF SYNC`. For demos, see §7.
- **`syncstate`** (`mmulti.h`): "Missed Network packet!" is drawn when it is non-zero, but mmulti never sets it (§3).

## 12. Brief 01: mmulti over vnet, and the test hooks

What brief 01 added (jfbuild `include/mmulti_vnet.h`, `src/mmulti_vnet.c`; the game's `src/game.c`, `src/sync.c`, `src/net.h`, `src/player.c`; tests in `tests/net/`).

**Where vnet sits.** `mmulti.c`'s four socket users hand over to `mmulti_vnet.c` when `-relay` was given: `netinit` (opens a vnet relay context and one vnet socket on the game port), `netsend`, `netread` (both pump the relay with `vnet_poll()` and so do `getpacket`/`flushpackets`/`sendpacket`/`initmultiplayerscycle` through them), `netuninit` (closes the context, which sends the relay a LEAVE; an `atexit` handler does the same when the game calls `exit()`). Peer addresses stay AF_INET `sockaddr_in` values inside `otherhost[]`/`snatchhost`: the relay's `10.0.0.N` and the port, so `issameaddress`, `presentaddress`, `savesnatchhost` and everything else in `mmulti.c` is unchanged, and `domain` is `PF_INET`. A vnet address maps one to one (`vnet_addr` family 4, `bytes[0..3]`, host-order port). The diff to `mmulti.c` is about 70 lines, all additions.

**Arguments** (read by `initmultiplayersparms`, after `-net`; `mmulti_vnet.h` has the full text; `-host-room N` takes 2 to 8, clamped to 4 on shareware): `-relay HOST:PORT` (UDP address of the relay, default port 7777; `udp://` prefix accepted; a `ws://`/`wss://` URL is refused natively), `-host-room N`, `-room CODE`. The room creator is `10.0.0.1` and is always player 0 / the master; joiners are slaves and take the next open slot as on plain UDP. The room itself (created by `VNET_BACKEND_RELAY_AUTO`, natively relay-over-UDP) has no player count: that is the master's `numplayers`, and the relay's member limit (`-max-members`, default 8, cap 253) is one number for the whole relay. All players use the same in-room port (`0x5bd9` or `-p`), because the virtual addresses already differ. A joiner pings `10.0.0.1:port` exactly as it pings a `host:port` on UDP and the master learns its address from the ping, so the start-up protocol (code-facts §3) is untouched.

**Start-up and failure.** `initmultiplayerscycle` first calls `mmulti_vnet_cycle`, which pumps the relay and returns CONNECTING (keep waiting), READY or FAILED. On READY the host prints `mmulti: room code ABC234 (...)` (stdout, the log, the OSD; stdout is flushed) and clamps `-host-room N` to the game's cap (`mmulti_vnet_setplayercap(MAX_SW_PLAYERS)`, set by `InitGame` just before the wait: 4 on shareware, 8 registered, which is what keeps `MultiSharewareCheck` from ever calling `exit(0)`) and to the relay's room size (`vnet_status_info.max_members`), each with a message. On FAILED the wait loop ends and `InitGame` prints `Network game failed: ...`, shows the same in a message box (`wm_msgbox`) and exits with status 1. Errors in the arguments or in creating the relay context (`optfail` in `mmulti_vnet.c`) set the same FAILED state, and `app_main` exits 1 at once instead of falling back to a single player game the way a plain `-net` failure does. Plain `-net` is unchanged in that and in everything else (a failure there still plays single player; the wait has no time limit).
Limits added only for relay games, because a relay room outlives its players: a slave that has heard nothing from the master 15 s after entering the room fails with "the host did not answer: the room may be full or the host has left"; a slave whose master stopped answering during the start-up wait fails after 10 s ("the host stopped answering"). Once the game is running, host loss is as before (the lockstep waits). The vnet context uses `keepalive_ms` 1000, `relay_timeout_ms` 10000, and its log sink prints warnings and errors.

**Impairment.** `VNET_IMPAIR` in the environment reaches vnet (`ignore_env` is left 0): `VNET_IMPAIR="loss=5,dup=2,reorder=3,lat=20,jit=10,seed=7" ./sw -net -relay ...` (give every process its own seed).

**Test-only arguments** (`sync.c`, declared in `net.h`; they print a `TEST:` line and are not for players): `-testsync` sets `NumSyncBytes = 8`; `-testquit<N>` makes `RunLevel` call `TestQuitFinish` once `MoveThingsCount >= N` (game tics since the level started; a process catching up can play a few more than N), which logs `TEST: quitting after T game tics: C sync checks, M mismatches, B sync bytes, player I of P`, keeps pumping `flushpackets()` for 1.5 s so a laggard still gets its acks, then sets `QuitFlag` (the normal exit, status 0, with `TerminateGame`'s own `ErrorCorrectionQuit`); `-testnudge<T>` moves this process's own player 8 units in x at tic T (a deliberate desync: it changes the simulation on this process only, and only when given). Same value on every player: `SendVersion`/`CheckVersion` carry `GameVersion + TestVersionSalt()` (sync bytes and quit tic folded in), so players started with different values print `CheckVersion(): player N has version ...`. ## 13. What brief 02 found (browser port)

Checked by building and running the game under Emscripten 6.0.13 (software renderer) in headless Chromium.

- **Platform detection (corrects §9).** Under `emcc`, `TARGETMACHINE` is `wasm32-unknown-emscripten`. `jfbuild/Makefile.shared` and `jfaudiolib/Makefile.shared` now map it to `PLATFORM=EMSCRIPTEN`; without that, `sdl2-config` found on `PATH` is the host's (wrong include paths), and the `pkg-config` GTK probe finds the host's GTK. `HAVE_STARTWIN` follows from `HAVE_GTK` in `src/game.c:3364-3370`, so no engine change was needed to drop the startup window.
- **`mmulti.c` does not compile for the browser** (`IP_RECVDSTADDR`, `IP_SENDSRCADDR`, `recvmsg` cmsgs). The browser build linked `mmulti_null.c` (single player) until brief 04 (§15), which compiles the plain UDP code out under `__EMSCRIPTEN__` instead.
- **`__linux` is not defined by emcc**, so `jfbuild/include/compat.h` found no endianness; an `__EMSCRIPTEN__` block was added.
- **A signature mismatch that x86 tolerated.** `SpawnBreakFlames` is defined with two parameters (`weapon.c:10931`) but `break.c` declared it with one and called it with one. `wasm-ld` warns, and the call would trap when a burning breakable is destroyed. `break.c` now declares and passes the second (unused) argument. There were no other `wasm-ld` signature warnings. Calls through function pointers cast to another signature would trap at run time instead of warning; none showed up in the demo runs, but the whole game is not covered by them.
- **Blocking loops.** The list in §5 is complete for what ran: every wait polls `handleevents()`, so a yield in `handleevents()` (after 8 ms without one) plus one in `showframe()` (a `requestAnimationFrame` wait) is enough. No loop in the engine, `jfmact` or `jfaudiolib` sleeps or spins without reaching one of them.
- **Fullscreen.** The default `sw.cfg` asks for fullscreen; in the browser `setvideomode()` always makes a window (browser fullscreen needs a user gesture and is the page's business).
- **Message boxes.** SDL's `SDL_ShowSimpleMessageBox` is an `alert()` that shows only the title under Emscripten, so `wm_msgbox()` prints the text and hands it to the page (`Module.jfswMessage`); the page shows it when the game exits.
- **Audio.** SDL's Web Audio device is always 32-bit float. `jfaudiolib/src/driver_sdl.c` rejected it ("audio format ?!", "FX driver is No Sound"); under Emscripten it now opens the device without an "obtained" spec so that SDL converts.
- **Timer.** `SDL_GetPerformanceCounter` is `performance.now()` based. A hidden tab pauses `requestAnimationFrame`, so `showframe()` waits at most 100 ms, and `sampletimer()` never advances `totalclock` by more than a quarter second at once (a long stall is a pause, not a burst of catching up).
- **Shareware quit.** Quitting a level (F10, Y) shows the "Give up?" Sybex page, which waits for a key before `exit(0)`.
- **A native bug found while recording demos.** `DemoTerm()` (`demo.c:330`) closes the demo file when a level ends, but a player who dies and restarts the level goes on recording into the closed `DemoFileOut`: the next full buffer (2048 packets, about 50 s) crashes `sw` with a segmentation fault in `DemoWriteBuffer`. A demo that is being recorded therefore ends at the player's death. Not fixed (not in scope).
- **Demo format.** `SW_PACKET` is 12 bytes (`short vel, svel; char angvel, aimvel; int bits`, padded), the header is 75 bytes, a recording is whole 2048-packet buffers followed by a -1 record. `LONG` is `int` (`mytypes.h:128`), so none of the `fwrite`n structs change size between x86_64 and wasm32: demos recorded on either load on the other (see the Outcome of brief 02 for the runs).
- **For brief 03: the GRP is re-checksummed on every start.** The page writes `/data/sw.grp` afresh each time, so its mtime changes and `grpscan.c` recomputes the CRC32 of the 26 MB file (about a second) instead of trusting `grpfiles.cache` (which is itself in the persisted folder). Brief 03 keeps the mtime stable (`FS.utime` to the cache record's stored time, section 14).
- **Config is written when the menus are left (browser only).** `sw.cfg` is otherwise only written at exit (`ShutDown()`, `TermSetup()`), which a closed tab never reaches; `ExitMenus()` in `src/menus.c` calls `CONFIG_WriteSetup()` under `__EMSCRIPTEN__`. A setting changed and then reloaded while the menu is still open is lost.
- **A save writes `savegame symbols missing.txt`** (a debug file, opened for writing many times per save) next to `game0.sav` in the current directory; the page's sync trigger ignores it.

## 14. What brief 03 found (game data in the page)

- **No engine change was needed.** The page writes `/data/sw.grp` and sets its modification time with `FS.utime` to the second the cache record was stored. `grpscan.c` keys `grpfiles.cache` (in the persisted cwd) by name, size and `(int)st_mtime`, so on the second start it finds a hit and prints no `Checksumming` line (the test checks the game's output). A different file under the same name (a picked registered GRP instead of the shareware one) misses once and is checksummed once (about 1 s); the cache keeps one entry per name, so switching back misses once more.
- **The name is `sw.grp` whatever the data is** (shareware included). That is fine: `IdentifyGroup()` falls back to the first recognised GRP when the wanted name is not found, and the CRC32 and size decide what the file is.
- **The CRC32 in JavaScript** is slice-by-4 over a `Int32Array`, run on each chunk as it arrives (so it overlaps the download). 26 MB takes about 95 ms in headless Chromium (30 ms in Node), so no worker was needed.
- **`fetch` is called with `cache: 'no-store'`**: otherwise the browser keeps a second 26 MB copy in its HTTP cache and "Download again" could be answered from it.
- **A truncated download is reported by the browser in two ways**: a connection that drops before `Content-Length` bytes arrived makes `reader.read()` reject (`net::ERR_CONTENT_LENGTH_MISMATCH`), while a short file with a correct, smaller `Content-Length` arrives intact; the declared size (or the table: starts with `KenSilverman` and shorter than a known GRP) catches that one.
- **With `Content-Encoding`, `Content-Length` is the compressed size** and the stream the page reads is already decompressed; progress uses the declared size, or none (indeterminate).
- **A CORS block and a network failure are both a `TypeError` from `fetch`** (as the brief said); the page's message says both and adds the CORS hint when the URL's origin differs from the page's.
- **Storage:** `navigator.storage.persist()` is asked after the first successful store. Chrome decides silently by itself (granted for installed or often visited sites, bookmarked, etc.; denied in a fresh profile, as in the tests); Firefox asks the person with a prompt. A quota failure arrives as `QuotaExceededError` from `put()` or from the transaction's `abort`; both go to the same handler.

**Hidden tabs.** (`jfbuild/src/sdlayer2.c`, `src/game.c`, `src/net.c`.)
- *What the tab is.* `jfbuild_browser_hidden_netgame()`: `document.hidden` and a relay session exists (`mmulti_vnet_active()`). A hidden single player game is not one: it behaves exactly as in brief 02 (frame yield with the 100 ms timer, about 10 tics a second measured; the test checks that no hidden-tab pass happens and the picture is still asked for).
- *The wake.* `mmulti_vnet.c` sets `vnet_config.wake`; its callback calls `jfbuild_browser_wake()` (an `EM_JS` function; it runs while `main` is suspended by ASYNCIFY, which is fine because it neither yields nor calls back into the game), which posts a message on a `MessageChannel`; the handler resumes the game if it is waiting in a hidden yield (`Module.jfswPending`). The wake is ignored while the tab is visible (animation frames pace it). A hidden yield (`browser_yield` now takes the hidden flag from C) ends on a network event (reason 1), on `visibilitychange` (2) or on a 250 ms timer (0; Chromium and the test's imitation run it at 1 Hz), which is what keeps vnet's own deadlines running; `handleevents()` yields on every call in that state (otherwise a loop with nothing to do spins for 8 ms between yields). In the measured hidden games 99.6 % of the resumes were network events.
- *The pass.* In a hidden network game `RunLevel` calls `HiddenNetPass()` (net.c) and draws nothing (no `drawscreen`, so no `showframe()`; `SetRedrawScreen` when the tab becomes visible again). **`faketimerhandler()` is where a player's input for a tic is made and handed to `sendpacket()`**, and the engine calls it from inside its drawing code (`engine.c`, `build.c`, many places; `domovethings` also calls it from long loops), so a pass that does not draw must call it itself; without that call the whole room stops after the hidden tab's last input (tic 131 and 127 in the mutation run). `faketimerhandler` makes at most one input per call and only when `totalclock` says one is due, so the pass calls it once and then again while an input is still due (at most 8 times: catching up to the tab's own clock, never ahead of it).
- **Sending is rate-limited, and that matters for a tab with no frames** (review finding S1; an earlier version of this section and of the code comment said "sent at once", which was wrong). `sendpacket()` appends to mmulti's output queue and calls `dosendpackets()`, which puts at most one datagram per peer on the wire every 25 ms (`PAKRATE 40`; `mmulti.c`). `faketimerhandler()` calls `getpackets()` first, which reaches `getpacket()` and so `dosendpackets()`, which may spend the window on an acknowledgement; the new input's own call is then refused and the input waits for the next call, which for a visible tab is the next frame. A hidden tab would have waited for the next network event (about 100 ms in the thinned-wake test: median 98 ms, p95 107 ms; at normal wake rates about 32 ms median). The fix (second version; the first spun): `mmulti_vnet_flush()` (mmulti.c, next to `mmulti_vnet_sendpending()`; `unsent[]` is set by `sendpacket` and cleared when `dosendpackets` sends) lets the held-back datagram out now, ignoring `PAKRATE`, and `HiddenNetPass` calls it once after `MoveLoop`. Native builds and visible tabs never call it, so their sending is unchanged; it changes when a datagram goes, not what is in it. The datagram rate is bounded by the pass rate. The first version re-posted a `MessageChannel` message while anything was held back (a "kick"), which kept a core busy: about 1,000 passes a second (27,000 to 47,000 hidden yields in a 35 s game); a coordinator review rejected it.
- *Tests for it.* `Module.jfswOwedLog` has one entry per hidden yield that was entered with data still held back. With the flush: 7 of 1,132 (hidden slave) and 7 of 1,444 (hidden host); without it (mutation) 1,133 of 1,141. The CPU check counts hidden passes (yields) a second while hidden: **31 a second (hidden slave), 40 (hidden host)**, bound 150; with a spin reinstated (mutation) 1,044. `?wake_every=N` (test only) lets only every Nth vnet wake-up through.
- *The clock does not hold the tab back.* `sampletimer()` still runs in real time inside the pass (its quarter-second cap is not reached: a pass comes with every network event, 40 a second or more), so a hidden tab's inputs fall due exactly as a visible tab's do. A first version also let a hidden tab make inputs ahead of its clock (up to 2 ahead of the furthest other player) and let a hidden master relay on its own; both were measured and removed: the room kept 40.0 tics a second without them (the same, and a 3 s stall of the hidden tab left the room 0.8 to 1.1 s late either way), because the game already catches a slow slave up (`faketimerhandler`, slave code: `totalclock -= synctics * i` by the lag it measured). A visible master relays only inside its own `faketimerhandler` (when it makes its own input), up to a tic (25 ms) after a slave's input arrived; unchanged.
- *Measured* (headless Chromium, software-rendered canvas, 4 shared cores, load average 3 to 5): a hidden, throttled slave and a hidden host both keep 40.0 tics a second on the other machine and their own, measured from 100 tics after the tab was hidden (it was hidden at tic 120 to 145) to tic 1450; with the wake handler emptied: 0 wake-ups, the room crawls (see the Outcome).
- *A frozen tab* (main thread blocked for 5 s): the other machine moves 2 or 3 tics in that time and stands still; the relay, vnet and the game carry on after it (vnet restarts its silence clocks when more than a keepalive interval passes between two polls). Frozen for longer than the relay's session timeout (relay `-session-timeout 3s -keepalive 1s`, the `relay-lost` scenario) the relay drops the member and that machine's game ends with the message above. Against a normal relay (15 s) a 20 s freeze of a WebSocket slave was survived in one trial (the browser answers the relay's pings itself).

**The per-machine record.** `-testdump<name>` (`sync.c`, `TestDumpTic()`, called from `TestTicHook()` in `domovethings`) writes 17 bytes per game tic, flushed: `MoveThingsCount` (4, little endian), the nine sync functions' bytes (computed there with `SyncFunc[]`, whatever `NumSyncBytes` is, so it does not depend on `-testsync`), and a 32-bit FNV-1a hash of the random seed, every connected player's full x, y, z, angle, horizon, bcnt and health, every sprite's index, full x, y, z, angle, picnum, statnum and sector, every sector's floor and ceiling height and every sector object's position and angle (since brief 04b also every sector's ceiling and floor stat, and not the angle of the picture override markers, which the drawing code uses as scratch space: §16). ## 16. What brief 04b found (input-to-tic delay)

Measured with `-testlag` (`sync.c`) in `tests/web/netplay.js` (`lag`, `lag-matrix`); numbers and load are in the brief's Outcome.

**Where a player's input waited** (both as the coordinator found, now measured):
- *The send window.* `faketimerhandler()` calls `getpackets()` before it makes the input, which reaches `dosendpackets()` for every peer; when 25 ms had passed that sent a datagram with acknowledgements only, and the new input's own `sendpacket()` then found the window used (`PAKRATE`, mmulti.c). The input waited for the next `dosendpackets()`: 25 to 29 ms at the median in a browser (frames), 13 to 15 ms natively, every time, on both master and slave. 04b: `SendInputNow()` (net.c) calls `mmulti_vnet_flush()` right after the input or the combined packet is queued, in every network game (relay and plain UDP: the function is in `mmulti.c` and works on any peer; its name is brief 04's). Datagrams with only acknowledgements or resends still go at most once per window, so a peer gets about one datagram per input plus the acks: 45 to 72 a second instead of 24 to 39 (1.8 to 2.0 times). **Many of those are redundant**: `getpackets()` (called before the input is made) reaches `getpacket()` and `dosendpackets()`, which, when the window has passed, sends a datagram with acknowledgements only just before the flush sends the input with the same acknowledgements and every unacknowledged packet. A slave sends about 20 to 25 such a second (590 to 762 of about 1,800 to 2,100 in a 30 s `lag` game; the `-testlag` log line counts them), a master 2 to 20. Not changed; a later cut (skip an ack-only datagram when an input follows in the same pass, or make the input before receiving) needs a change to mmulti's pacing. Brief 06: size the relay for about 70 datagrams a second per player and direction.
- *The master's forwarding.* The master built the combined packet only in its own `faketimerhandler()`, after its own input. A slave's input that completed a tic waited for the master's next input: mean 3 to 7 ms with a browser master, 10 to 14 ms with a native master and a browser slave or 30 ms latency, p95 17 to 24 ms; 0 between two unimpaired native games, whose 120 Hz timers keep the master's own input last. 04b: the loop is `MasterForward()`, called from `faketimerhandler()` as before and from `getpackets()` **after** its receive loop (`packbuf` is the receive buffer and the send buffer; calling it from inside the loop overwrites the rest of the packet being read: see the mutation in the Outcome). The same inputs and the same order of tics; the lag-correction bytes of every 32nd tic (`myminlag`, measured at each of the master's own inputs, sent and reset every `TIMERUPDATESIZ` tics) and how many sync records go in each packet (`AddSyncInfoToPacket`, up to 4 of those ready) follow when the master sends, as they always did.
- *What is left.* A browser slave's input (unimpaired, two browsers) now comes back complete after about 42 ms (85 before) and the complete tic then waits about 34 ms in the lockstep buffer (14 to 30 before): the lag correction (`bufferjitter`, set from the jitter it measures) holds a browser slave's tics longer than before, which gives back part of the saving (why it settles higher was not looked into). The buffer is the larger remaining cost in browsers; it is the lag-correction algorithm, out of scope here. A native slave's buffer wait is 0.1 to 8 ms.
- *The lag correction still settles.* On the slaves `otherminlag` settles at -1 to 4 and `bufferjitter` at 1 tic (native slaves) or 3 to 9 (browser slaves, the higher ones with 30 ms each way); after tic 200 the clock was corrected not at all in 13 of 16 `lag-matrix` slave games and by 3 or 6 clock ticks in the others; in the `lag` runs at most one correction after tic 200 and never a reversal (the test checks this).

**`-testlag`.** One record of nine 32-bit fields per game tic, from this machine's clock (`CLOCK_MONOTONIC`, microseconds): tic, made (own input), ready (every input here), ran, sendwait (sendpacket to datagram, through two test-only hooks in `mmulti.c`, `mmulti_test_queuehook` and `mmulti_test_sendhook`), fwdwait (master: ready to the combined packet), `otherminlag`, `bufferjitter`, the clock corrections so far. A record is written 16 tics after its tic ran, because on the old code the datagram (and on the master the combined packet) often left only after the tic had run; written at once, exactly those waits would read "unknown". The log line `TEST: lag: N datagrams (B bytes) to player P in T ms` gives the rate.

**The tic 1 difference** (bugs.md L19). The drawing code (`FAF_DrawRooms`, draw.c) saves a sector's ceiling or floor stat and picnum in the `ang` and `xvel` of the ceiling/floor picture override marker sprites (`STAT_CEILING_FLOOR_PIC_OVERRIDE`, E1L1 sprites 51 and 924) while it draws, and restores the stat with the parallax bit cleared. After one frame the marker's `ang` is 1, after more it is 0. A machine that ran tic 1 after a single frame (a browser whose first frame came late runs several inputs and tic 1 straight after it) therefore had a different state hash for the first 1 to 8 tics. Nothing else reads those fields. `TestStateHash()` leaves the markers' angle out and hashes every sector's ceiling and floor stat instead, since the first frame clears the parallax bit of the two override sectors for good and the game reads it (shots into a parallax sky). A browser tab that is hidden before its first frame never draws (brief 04's hidden pass) and keeps the bits: its sector state differs from tic 1 on, and missiles (`move_missile`), a player landing on a parallax floor (`DoPlayerTestPlaxDeath`), z ranges (`SectorZadjust`), splashes and hitscans read them every tic: a desync (L19, open; the user decides where it is fixed).

**`-teststate[<T>]`.** With `-testdump<name>`, `<name>.state`: the whole state as text, one line per object (globals with `randomseed`, `numframes` and `krandcount`; every connected player; every live sprite, its User and its pointers as indices; every stat list; the head of the free list; every sector with its sprite list and SectUser; every wall; the sector objects; `Anim`; the interpolations; the hash), when `RunLevel` starts and at the start of tics 1 to 3 and T. Code and data addresses are written as offsets (`...@`), equal only within one build. About 1.3 MB per dump on E1L1; the first one delays a browser's first frame enough to make the tic 1 case happen in most games (which is what `tic1` uses).

**`-testslowstart<ms>`** (test-only; inert without it): the machine waits that long when the level starts (after `InitRunLevel` and the `-teststate` start dump, before the first frame) with its clock running; in the browser by `emscripten_sleep` (a busy wait also stopped the other test pages in the same Chromium renderer), natively by a busy wait. Given to the master it makes the uneven tic 1 certain: its one frame makes all due inputs, the slave's first input is already there, and tic 1 runs straight after it. It flushes mmulti first: the packet `waitforeverybody()` queued last can be held by the send window until the machine polls again, and the others then stay in their own `waitforeverybody()` meanwhile (an original-game property: harmless while every machine goes straight into its game loop).

**The `-testlag` clock** is `CLOCK_MONOTONIC` (POSIX, Emscripten) or `QueryPerformanceCounter` (`_WIN32`, declared in `sync.c` so that it need not include `windows.h`): microseconds. (`getusecticks()` is milliseconds under SDL.)
